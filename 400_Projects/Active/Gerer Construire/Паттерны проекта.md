# Паттерны 

## Repository Pattern Inverted Pattern 1

### 🧩 Суть "на пальцах"

Вместо того чтобы делать запрос `http.get` прямо в компоненте или сервисе, мы создаем **три слоя**:

1. **Интерфейс (Домен):** «Пустой» файл (абстрактный класс), который просто говорит: _«Мне нужны данные в таком-то формате»_. Это наш контракт.
    
2. **Реализация (Инфраструктура):** Файл, который реально лезет в интернет или базу.
    
3. **Инверсия (DI):** Мы связываем их в настройках модуля/конфига.
    

### 🏠 Аналогия

- **Компонент (Мужик):** Хочет хлеб. У него есть «записка» с надписью «Хлебовоз». Ему плевать, кто именно его привезет.
    
- **Репозиторий (Записка):** Тот самый интерфейс.
    
- **Сервис (Представитель):** Тот, кто увидел записку и реально пошел в пекарню (на бэкенд).
    

### 🚀 Почему это круто для фронта?

- **Работа без бэкенда:** Ты не ждешь API. Создаешь «фейковый» репозиторий с моками (простыми данными), пишешь весь фронт, а когда бэк готов — просто подменяешь класс в одной строчке конфига.
    
- **Чистота:** Компоненты не знают про URL-адреса, заголовки и специфику HTTP. Они просто просят данные.
    

### ⚠️ Критика (что важно понимать Mid-у)

- **Coupling (Связность):** Домен всё равно «знает» о существовании репозиториев. Мы не изолировали его магически, мы просто перенесли зависимость на интерфейс.
    
- **Импорты:** В тестах тебе всё равно придется импортировать файл интерфейса.
    
- **Главный риск:** Если ты запихнешь в интерфейс что-то специфичное для бэкенда (например, типы ошибок конкретной библиотеки), инверсия станет бесполезной. Интерфейс должен диктовать **твои** условия, а не условия бэкенда.



## Pattern 3: Dependency Injection at the Provider Level

### 🎯 В чем суть?

Это переход от **автоматического** управления зависимостями Angular (`providedIn: 'root'`) к **ручному** (через массив `providers`). Мы сами решаем, какой класс создать и что в него передать.

### 🛠 Как это выглядит в коде

Вместо того чтобы полагаться на магию декоратора `@Injectable`, мы явно прописываем логику создания объекта:

TypeScript

```
providers: [
  // 1. Связываем токен (интерфейс) с конкретной реализацией
  {
    provide: USER_REPOSITORY_TOKEN,
    useClass: HttpUserRepository, 
  },
  // 2. Ручное создание UseCase через фабрику
  {
    provide: GetUserUseCase,
    useFactory: (repo) => new GetUserUseCase(repo),
    deps: [USER_REPOSITORY_TOKEN], // Список зависимостей для конструктора
  },
]
```

### 🧠 Почему это важно для Senior/Middle?

1. **Чистый Domain (Голые классы):** Твой `UseCase` становится обычным TypeScript-классом. В нем нет декораторов `@Injectable`, нет привязки к Angular. Его легко тестировать и легко перенести в другой проект/фреймворк.
    
2. **Explicit Dependencies (Явность):** Глядя в массив `providers`, ты сразу видишь «дерево» зависимостей. Это исключает ситуацию, когда зависимости возникают из ниоткуда и создают «циклические ссылки» (Circular Dependencies).
    
3. **Гибкость тестирования:** Ты можешь в любой момент заменить `useClass: HttpUserRepository` на `useValue: MockUserRepository` прямо в описании провайдеров для тестов.
    
4. **Контроль создания:** `useFactory` позволяет добавить логику при создании: например, проверить какое-то условие или выбрать одну из двух реализаций сервиса на лету.
    

### 🚦 Когда использовать?

- **Всегда в слое Domain:** Чтобы бизнес-логика оставалась «голой» и независимой.
    
- **Когда есть интерфейсы:** Чтобы связать абстракцию с реальным HTTP-сервисом.
    
- **В больших проектах:** Где важно контролировать каждый импорт и избегать каши из зависимостей.
    

### ⚠️ Цена вопроса

- **Boilerplate:** Нужно писать больше кода (те самые `providers`, `useFactory`, `deps`).
    
- **Порог входа:** Джунам сложнее разобраться, почему сервис не инжектится «сам по себе».
