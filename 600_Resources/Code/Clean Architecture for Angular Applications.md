## Summary
[Brief overview of what this resource is about]

Данный документ представляет собой подробный обзор концепции «Чистой архитектуры» (Clean Architecture) применительно к разработке фронтенд-приложений на базе Angular. Основная цель этого подхода — отделение основной бизнес-логики от деталей реализации, таких как пользовательский интерфейс, базы данных и сторонние фреймворки.

Внедрение Чистой архитектуры решает проблему непоследовательности кода и сложности масштабирования, обеспечивая тестируемость и гибкость системы. Ключевым принципом является направление зависимостей: от внешних слоев (презентационного) к внутренним (доменному). Это позволяет изменять технологии или интерфейс без необходимости переписывать ядро приложения.

## 1. Необходимость архитектуры во фронтенд-разработке

Существует заблуждение, что фронтенд не нуждается в сложной архитектуре. Однако отсутствие четкого плана проектирования ведет к негативным последствиям:

- **Проблема несогласованности:** Без архитектурных стандартов разработчики принимают решения индивидуально (аналогия со строителями, один из которых использует камень, а другой дерево), что делает структуру здания (приложения) нестабильной.
- **Риск коллапса системы:** Несогласованный код затрудняет поддержку и может привести к невозможности реализации запланированной структуры.
- **Преимущества архитектурного подхода:**
    - Обеспечение консистентности кода.
    - Повышение тестируемости.
    - Возможность адаптации к изменениям бизнес-требований.
    - Масштабируемость и четкое видение финального продукта.

## 2. Основы Чистой архитектуры

Чистая архитектура является адаптивной и структурированной методологией, которая вобрала в себя идеи из предметно-ориентированного проектирования (DDD) и других архитектурных подходов:

- Гексагональная архитектура (Hexagonal Architecture).
- Луковая архитектура (Onion Architecture).
- Архитектура вертикальных срезов (Vertical Slice Architecture).

### Основной принцип

Главная идея заключается в разделении бизнес-логики и логики приложения так, чтобы изменения в одной части не влияли на другую. Домен (сущности) должен быть полностью независим от презентационного слоя, баз данных и инфраструктуры.

**Правило зависимостей:** Зависимости всегда направлены снаружи внутрь. Презентационный слой зависит от домена, но домен никогда не зависит от презентационного слоя.

## 3. Слои приложения и структура папок

Для реализации Чистой архитектуры в Angular предлагается разделение проекта на три основных слоя в директории `src/`:

### 3.1. Доменный слой (Domain)

Содержит ядро бизнес-логики. Этот слой должен быть максимально независим от фреймворка (Angular). Изменения здесь происходят только при изменении бизнес-требований.

- **Модели (Models):** Описание бизнес-сущностей.
- **Варианты использования (Use Cases):** Описание конкретных действий системы.
- **Абстракции репозиториев:** Интерфейсы для взаимодействия с данными.

### 3.2. Слой данных (Data)

Отвечает за реализацию доступа к данным и их обработку.

- **Реализации репозиториев:** Конкретный код, выполняющий запросы.
- **Сущности (Entities):** Модели данных в том виде, в котором они приходят из API/БД.
- **Мапперы (Mappers):** Преобразователи между сущностями слоя данных и моделями доменного слоя.

### 3.3. Презентационный слой (Presentation)

Включает в себя всё, что касается пользовательского интерфейса.

- Компоненты Angular.
- Стили и шаблоны.
- Логика отображения, которая использует Use Cases для получения данных.

## 4. Процесс реализации на примере Angular

### Базовые элементы

Для обеспечения структуры создаются базовые абстракции:

- **Mapper:** Абстрактный класс с методами `mapFrom` и `mapTo` для трансформации данных между слоями.
- **UseCase:** Интерфейс с методом `execute`, который возвращает `Observable`.

### Доменная логика (User Application)

1. **UserModel:** Определяет атрибуты пользователя (ID, имя, email и т.д.) исходя из потребностей бизнеса, а не формата API.
2. **UserRepository:** Абстрактный класс, описывающий методы (login, register, getUserProfile).
3. **Use Cases (UserLoginUseCase и др.):** Отдельные классы для каждой операции. Они внедряют `UserRepository` и вызывают соответствующие методы. Разделение на разные файлы облегчает управление и предотвращает влияние изменений в одном сценарии на другие.

### Реализация данных

1. **UserEntity:** Описывает структуру данных, получаемых от API (может отличаться от `UserModel`).
2. **UserImplementationRepositoryMapper:** Реализует логику преобразования `UserEntity` в `UserModel` и обратно.
3. **UserImplementationRepository:** Конкретная реализация репозитория, использующая `HttpClient` для выполнения HTTP-запросов и маппер для обработки результатов.

### Интеграция в Angular (DataModule)

Связывание абстракций и реализаций происходит в модуле данных через провайдеры:

- Используются фабричные функции (`useFactory`) для создания экземпляров Use Cases.
- Определяются зависимости для каждого провайдера.
- Абстрактный класс репозитория связывается с его конкретной реализацией через `useClass`.

|   |   |   |
|---|---|---|
|Компонент|Слой|Ответственность|
|**UserModel**|Domain|Бизнес-определение сущности «Пользователь»|
|**UserUseCase**|Domain|Изолированная логика конкретного действия|
|**UserRepository**|Domain|Контракт (интерфейс) для работы с данными|
|**UserEntity**|Data|Структура данных внешнего API|
|**UserImplRepository**|Data|HTTP-запросы и техническая реализация|
|**Component**|Presentation|Отображение данных и вызов UseCase|

## Заключение

Применение Чистой архитектуры в Angular позволяет создать гибкую систему, где доменная логика защищена от изменений во внешних слоях. Несмотря на то что в данной реализации домен зависит от языка (TypeScript), он остается полностью независимым от фреймворка Angular. Это гарантирует, что при смене технологий или обновлении UI-библиотек ядро приложения останется нетронутым и работоспособным.
